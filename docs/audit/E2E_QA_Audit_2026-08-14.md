## 1. Executive summary & verdict

The **deterministic engine is the strong part of this product.** Onboarding collects the right inputs, the split/prescription/volume/progression logic tracks the v17 workbook closely, and the safety **gates** (age, screening outcomes) and safety **floors** (reps ≥4, %1RM ≤88, RIR floors, volume 4–20, skill gate, solo-lifter handling) held on **109/109 engine profiles** and on my 9 hand-built profiles. Generated programs are coherent, goal-appropriate, progressive, and equipment-correct.

The **weak part is everything that surrounds it:** the AI coach cannot be exercised at all in the preview (it degrades to a shallow canned responder with no model, no memory, and no ability to change a program), a few onboarding answers are silently ignored, injury handling is softer than the workbook's own guidance, and short sessions are neither time-feasible nor volume-complete.

**Overall quality verdict: the engine is release-grade with fixes; the AI coach and its memory layer are NOT release-testable and NOT release-ready.**

**Release recommendation: NOT READY as a "personalized AI coaching experience." READY-WITH-CONDITIONS as a deterministic program generator + tracker** (coach kept behind its gate, which is its current production state).

Top blockers before "AI coach" can be claimed: (B) coach has no working backend/memory in any environment I can reach; (C1) injury programs still prescribe the workbook's own "avoid" patterns; (C2) two onboarding answers are dead; (D1) session-length is not honored.

## 4. Prioritized defect list

### CRITICAL (blocks the "AI coach" claim)
- **C-B. Coach is non-functional in every reachable environment.** [CONFIRMED] In demo/preview the coach is a keyword canned responder: no model, no memory of prior turns, no proposals, no program mutation. Two live examples below. Real AI path needs a signed-in non-demo internal build (owner infra). *Impact: the headline feature cannot be demonstrated or QA'd.*

### HIGH
- **C-1. Injury programs still prescribe the workbook's own "avoid" patterns.** [ENGINE] A knee-flagged user (MODIFY_AND_CONTINUE) received **Barbell Back Squat, Walking Lunge, Bulgarian Split Squat** — "deep knee flexion under load," the exact `avoidPatterns` string in `injuryModifications.ts` — at only +1 RIR, *while* knee-safe options (Leg Press, Hip Thrust, machine curls) were available and used. The data's `prefer: machine/supported/low-impact` steering and `downgradeIds = last-resort` intent are not enforced; the generator applies exclude-list + RIR bump + a soft score penalty that isn't strong enough to displace barbell squats. *Impact: unsafe-feeling prescriptions for the exact users who disclosed a limitation. Needs the accredited-professional review the workbook itself mandates.*
- **D-1. Session length is not honored; short sessions overshoot time and drop muscles.** [ENGINE] `maxExercises(30)=4`, but a 30-min FB3 session generated **6 exercises / ~20 working sets** (~50–60 min real) because required slots override the budget, and the only slots dropped were isolation — leaving **Triceps = 0 and Calves = 0 for the week.** *Impact: "impossible session" vs the promised 30 min; incomplete weekly coverage. Violates v17 §22 (30-min ⇒ ≤4 ex / ≤14 sets) and §23 "nothing trained zero."*

### MEDIUM
- **D-2. "Exercises you love" is collected, promised, and ignored.** [ENGINE+CODE] `preferred_exercise_ids` is stored and the UI says "we'll prioritise them," but the generator never reads it — programs are byte-identical with/without it. *Impact: broken promise, weakens personalization & trust.*
- **D-3. "Have you followed a structured program?" is dead.** [ENGINE+CODE] `followed_structured_program` is stored; the code comment claims it drives a conservative first block, but no generator/safety code reads it. An intermediate who never trained structured gets no extra caution. *Impact: contradicts v17 §1 and the onboarding copy.*
- **A-1. Age-policy wording is internally contradictory.** [CODE] Sheet 00/01 still describe a 16–17 "young-person + guardian" pathway; sheet 15 and the implementation are stricter (**18+ only, hard block, no guardian override** — engine-confirmed). Stale copy risks a reviewer/legal mismatch. *Fix the docs to match the stricter live behavior.*

### LOW
- **L-1. Coach welcome copy says "Powered by Google Gemini"** while the reachable build uses canned replies. [CONFIRMED] Misleading in any internal demo.
- **L-2. Rule-tag inconsistency:** some beginner exercises carry `{P01}`, siblings in the same session don't (e.g. Plank). [ENGINE] Cosmetic/audit-trail only.
- **L-3. Secondary-muscle floor not enforced** even in 60-min plans for Core (occasionally 3 sets). [ENGINE] Minor vs v17 half-target intent.

## 8. Firebase & memory architecture assessment

**Current reality [CODE]:** in demo/preview all "memory" is the local `AppState` blob (`chat`, `coachThread`, profile, program, sessions) in `sho.state.v1.anon`. The scripted coach reads live `AppState` (name, goal, streak, weight trend) but has **no turn-to-turn memory** and writes nothing back.

**The good news — a proper server memory model already exists in `firestore.rules` but is unwired:**

```
coachUsers/{uid}/
  memories/            conversationSummaries/   insights/
  proposals/           actions/                 proactiveState/   turns/
coachSafety/{uid}      ← Admin-SDK only, not client-readable/writable
config/coach           ← global kill switch / limits / guardrail prompt
```

All `coachUsers` reads are `isCoachOwner()` (own uid), **all writes trusted-server only** — users can inspect/export but cannot forge memories, proposals, consent, or replies. `coachSafety` is fully server-side. This is a strong, minimization-friendly, cross-user-safe design.

**Recommended memory model [REC]** (maps cleanly onto the existing scaffold — this is "populate what's scaffolded," not "rebuild"):

| Memory class | Store | TTL / policy |
|---|---|---|
| Stable profile facts (DOB, sex, experience) | `users/{uid}.backendUser` | until user edits |
| Goals & preferences (goal, focal, loves) | `users/{uid}.backendUser` + `insights` | until changed |
| Injuries/limitations/safety | `users/{uid}.backendUser.affected_regions` + `screening` | review after 4 symptom-free weeks (v17 §14) |
| Current program state | `programs/`, `progression_state/`, `workout_instances/` | versioned; keep prior on goal change (v17 GC09) |
| Workout history & performance | `sessions/`, `set_logs/` | retain; summarize old into `conversationSummaries` |
| Temporary conversational context | `turns/` → periodic `conversationSummaries/` | **expire raw turns after N days**; keep summary |
| Coach decisions + approved changes + reasons | `proposals/` + `actions/` | append-only audit; server-written |

**Required work before the memory layer is real [REC]:** wire the server coach to write `turns`/`memories`/`actions`; add a turn-summarization + expiry job (data minimization); surface an in-app "what the coach remembers" + correction/delete control (consent & GDPR-style rights); add composite indexes for `turns`/`sessions` by uid+time; and confirm `backendUser` write rules validate injury/screening edits. **No schema redesign is needed — the collections and rules exist.**

## 11. Final release recommendation

- **Deterministic generator + tracker (coach behind its gate): READY WITH CONDITIONS** — fix D-1, D-2/D-3, A-1; obtain accredited-professional sign-off on injury outputs (C-1). The safety envelope itself is solid and well-guarded.
- **"Personalized AI coach": NOT READY / NOT VERIFIABLE** — the coach cannot be tested in any environment available to this audit, has no working memory, and cannot action changes. Do not market or enable it until the real server path + memory scaffold are wired and re-audited end-to-end (C-B, §8), which is consistent with the product's own fail-closed gate.
